# Implementation notes: rule routing

## Phase 1: Routing data
### Design decisions
- `load:` inserted as the last key inside each rule's existing frontmatter block — HOME/repos/.claude/rules/*.md — no other frontmatter or body line touched; `always` x7, `native` x8, routed objects x4 per the Data Model classification table.
- Routed triggers transcribed from the "Routed triggers" table with the table's `\|` unescaped to `|` (the backslash only escapes the markdown table cell) — git.md, marquee.md, otto.md, voice.md — regexes are single-quoted YAML scalars so `\b` and `\.` stay literal.
- voice and git `prompt` are one single-element list holding the table's alternation regex, kept verbatim rather than split into one entry per alternative — voice.md, git.md — same match semantics, closest to the table.
- git's `tools` after-entry and gate-entry are separate list items; bash `after` entries are bare strings, gates are `{ match, gate: true }` — matches the Data Model syntax.
### Deviations
- None.
### Tradeoffs
- Single alternation regex vs. one list entry per alternative for `prompt` — table fidelity won; Phase 2's parser treats both identically.
### Open questions
- None. (Note for Phase 2: voice's `\bPR\b` is matched case-insensitively per the Data Model, so it also matches the word "pr".)
- Criterion outputs: `rg --files-without-match '^load:' HOME/repos/.claude/rules/*.md | wc -l` printed `0`; all 19 frontmatter blocks parse with a YAML loader and every bash regex compiles.

## Phase 2: Router library
### Design decisions
- Hand-written YAML subset parser for `load:` (scalar `always`/`native`, a block map of `prompt`/`tools`/`bash` whose values are flow values or `- item` lists, flow `[...]`/`{...}`, single- and double-quoted scalars, ` #` comments) — rules.ts:parseLoad, Flow, blockMap — rails has no package.json and runs inside the engine's worker, so no YAML dependency; anything outside the subset (a multi-line block-map item, an unterminated flow, an unknown key, a non-boolean `gate`) throws instead of being misread.
- `parseLoad` compiles every regex (case-insensitive) and rejects a trigger map with zero triggers — rules.ts:validate — a rule that parses also matches; a routed rule with no triggers would never load, so that is a parse error, not a silent drop.
- `buildIndex(files)` indexes a rule whose `load:` is missing or broken as `always` with the reason in `error` — rules.ts:buildIndex — the doc's run-time rule (stays in context, caller names it on the status line); the CI teeth are the live-dir test asserting no `error` on any rule.
- `splitInstructions` part body runs from the end of its header line to the next header, so it carries the blank-line separator; the preamble is `{ header: '', body }`; a header must start the text or follow `\n\n`; no header at all throws — rules.ts:splitInstructions — join is plain concatenation (byte-exact), dropping any middle section leaves a well-formed blob, and a framing change fails loud (the risk table's "split failure throws -> latch").
- Header regex accepts `Contents of /abs/path (<tier>):` and `Contents of <...> (<tier>):`; the `<managed-settings>` section carries no `path` — rules.ts:SECTION — per the API comment and Phase 0 (b).
- `nestedPath` accepts an optional ` (<tier>)` suffix — rules.ts:nestedPath — tolerant of the engine adding a tier to nested rows; the path still ends at the header line.
- `matchTool` reports a rule that both gates and rides as gate only — rules.ts:matchTool — once the gate delivers it, the after-inject is redundant.
- `normalizeStatement` strips leading `VAR=val`, `env` with its options (`-i`, `-u NAME`, `-C DIR`, `-S`, ...) and assignments, then git global options (`-C`, `-c`, `--git-dir`, `--work-tree`, `--namespace`, `--config-env` take a value; any other leading `-...` such as `--no-pager` is dropped); words are quote-aware and rejoined with single spaces — rules.ts:normalizeStatement.
- Fixtures are JSON beside the tests: `hooks/fixtures/instructions-2b8aebe2.json` (transcript `:19`, `rendered[0].content` minus the `<system-reminder>` wrapper, 68,183 chars, plus `files[]` path/tier) and `hooks/fixtures/nested-e9ef7f18.json` (`:191-205`, 15 rows, same unwrap, 57,861 chars). The unwrap is what the hook receives (typings: the wrapper goes around what the chain answers; Phase 0 (b) saw `instructions` open on the preamble).
- The fixture tests key the index under the recorded rules dir (`/home/saidler/repos/scottidler/claude/HOME/repos/.claude/rules`) while reading this checkout's rule text — rules.test.ts:RECORDED_RULES_DIR — the transcripts carry absolute real paths; this keeps the tests valid in any clone.
### Deviations
- `matchTool(index, tool, input, split)` takes a fourth argument, the Bash statement splitter — same effect, correct seam: the doc says Bash matching runs "after rails' existing statement split", which lives in index.ts (`heads` + `segment`); rules.ts importing index.ts would cycle once Phase 3 imports rules.ts. Tests pass `internals.heads`/`internals.segment`.
- Extra exports beyond the API block: `frontmatter`, `buildIndex`, `ruleAt`, `isRouted`, and the `RuleIndex`/`IndexedRule`/`InstructionPart`/`ToolMatch` types. The API used `RuleIndex` without defining how it is built; Phase 3 needs these.
- The success criterion's "18 parts with a `path`" is met as 18 file sections, 17 with a `path` and the `<managed-settings>` section without one, plus the path-less preamble (19 parts). The API comment says managed parts carry no path and Phase 0 (b) says "18" counts file sections; the test asserts 19 / 18 / 17 and the section order equals `files[]`.
- The settings.json tool-name test reads names from `permissions.{allow,deny,ask}` heads and the PreToolUse/PostToolUse `matcher` strings (expanding `a|b` and `x(a|b)` groups), plus one built-in, `ToolSearch`, which settings.json never names. Without that one name voice's ToolSearch trigger could not pass.
### Tradeoffs
- Subset parser vs. a YAML library — no dependency, no loader risk, and an explicit refusal of shapes it does not know; costs ~150 lines.
- Separators in the preceding body vs. in the following header — keeps `header` the exact header line; the cost is a trailing `\n\n` if Phase 3 drops the last section (whitespace only).
- `ruleAt`/`isRouted` scan a 19-element array vs. a Map — the index stays plain data (the ledger lesson about `$.state`), and 19 is nothing.
### Open questions
- `normalizeStatement` does not strip `sudo`, `command`, `exec`, or a path-qualified `/usr/bin/git`; the doc does not ask for them. Should `sudo git push` reach the git gate?
- Criterion outputs (2026-10-09, `main` after `f6f8036`): `splitInstructions` on 2b8aebe2: `parts 19 sections 18 with path 17`, preamble `"Codebase and user instructions are shown below. Be"`, path-less headers `(preamble)` and `Contents of <managed-settings> (organization-managed policy instructions):`; `join byte-exact true len 68183`. e9ef7f18: `paths 15 routed [ "marquee.md", "otto.md", "git.md", "voice.md" ]`, outside the index `CLAUDE.md`, `logging.md`, `cli.md`. `bun test`: `239 pass 0 fail 382 expect() calls` (147 before). `otto ci`: exit 0, `✅ All CI checks passed!`. rules.ts/rules.test.ts are not yet in `.otto.yml`'s lint list (Phase 4); `rg '—'` over both finds none.

## Phase 3: Wire the hooks
### Design decisions
- The five hooks are registered first in `register`, ahead of the four Bash hooks, so routing judges the call the model wrote and its context lands outermost; with `rule_routing` false they still register and the first dispatch latches routing off (quietly, no status line) and calls `$.ui.invalidate('prompt.attachment')` — hooks/index.ts:register — that is how flipping the toggle restores the full load mid-session; the module reloads on a config change but `register` has no `$`.
- The ledger and latch are working copies in module memory (`Router`), written through to `$.state` on every change and read back once per module load — hooks/index.ts:newRouter, loadRouter, persist — every claim (undefined to pending, pending to delivered) is one synchronous step, so two calls in one batch cannot both take a rule; a `$.state` compare-and-set loop would need fresh reads inside one dispatch, which the typings say read "one moment".
- The router is top-level functions over an explicit `Router` object, not a closure object with methods — hooks/index.ts — `claude plugin validate` refuses `rr.method($, ...)` ("$ itself is passed as an argument"); it follows `$` only into plain module functions.
- `$.state` values are declared in a contract file, `types/index.d.ts`, named as `"types"` in plugin.json — types/index.d.ts — validate requires every `$.state` key in the manifest's contract; index.ts imports the ledger types from it, so the module-load test now also allows `../` relative imports.
- `kept` maps a real path to the fingerprint (FNV-1a of type + text) of the attachment that kept it — hooks/index.ts:decideFiles, fingerprint — the same attachment asked again (any plugin's `invalidate('prompt.attachment')`) must not drop its own files as duplicates, which would hide CLAUDE.md and every always rule.
- A deny from a routed hook's own guard is computed before `next`; after-context is appended to whatever `next` returns, `isError` included, and a `deny` from below releases the claimed rules (they never reached the model); a `prompt.submit` dropped below releases the same way — hooks/index.ts:register, releaseRules.
- A gated call that also matches after-triggers denies only; the after rules are claimed on the retry. `session.compact` clears the loop when `trigger !== 'precompute'` and the result carries `messages` (precompute's result carries messages but installs nothing, per the typings).
- Rejoin keeps the blob's own trailing newline run: dropping the last section strips the predecessor's dangling `\n\n` and re-appends exactly what the blob ended with — hooks/index.ts:rejoin — tested both ways (blob ending without and with `\n`).
- A nested_memory with no `Contents of <path>:` header throws (framing changed), which latches; an instructions blob that splits to nothing already throws in `splitInstructions`.
- Log lines: `rules: keep|drop <basename> (<reason>) <real path>`, `rules: inject <basename> (<prompt|tool>) <path>`, `rules: gate <basename> (deny|pending, deny <tool>) <path>`, `rules: delivered ... (turn.step)`, `rules: skip <name> (leads to no file) <path>`; debug log always, transcript too when `debug` is on — hooks/index.ts:say — basename first so the AC's `rules: drop git.md` greps literally, the real path after the reason to tell the two CLAUDE.md files apart.
- Hook tests live in `rails/tests/routing.test.ts` (the kit's `tests` include dir), so `bun test` in `hooks/` never sees them; every noun rails calls is answered by the test's own `on` hooks, which must return `{ value }` (a throwing mock is skipped and reads as "no implementation", so the forced failure answers `{ deny }`).
### Deviations
- `kept` is `{ [realPath]: fingerprint }`, not `string[]` — same dedupe, plus the re-ask case above, which the Data Model's list cannot tell apart.
- The deny always ends with the draft clause ("If your text changes after reading it, show Scott the new draft before sending."), not only when the conversation already showed a draft — the hook cannot tell reliably whether a draft was shown; the clause is harmless when none was.
- Rule-index entries whose link leads to no file are skipped (debug line `rules: skip`), not read — found live: `~/repos/.claude/rules/cli.md` and `logging.md` are dangling links since `ba21860` moved both to `refs/`; the first headless smoke run read cli.md, got ENOENT, and latched the router off. The engine loads nothing from a dangling link either.
- The `instructions` and `nested_memory` real paths come from `$.fs.stat(path, { resolve: true })`, falling back to the spelling when it cannot resolve (cached per path for the module's life).
- The kit test's rule index is synthetic (the real classification, stub bodies) and the e9ef7f18 burst is its 15 recorded paths with stub bodies: the kit runs with no file system and imports only `.ts`, so it cannot read the JSON fixtures. The recorded text runs through the same `decideFiles`/`rejoin` under bun in index.test.ts.
### Tradeoffs
- Module memory plus `$.state` write-through vs `$.state` alone with `ifVersion` — atomic claims with no retry loop; costs one full-ledger write per change (a few KB at most).
- Latch on any `$.state` write failure vs best-effort persistence — a failed write is a router failure like any other, and the latch's direction (full load) is the safe one.
- Kit tests in `rails/tests/` vs a bunfig ignore pattern under `hooks/` — no extra config file, and it is the layout the typings' tsconfig names.

## Audit round 1 fixes
Implementation audit round 1, synthesis X6CMQgQe (`~/.cache/review-panel/runs/X6CMQgQe/synthesis.md`): 1 must-fix, 3 cheap wins and the Q3 wrapper answer folded; 1 deferred.
### Design decisions
- MUST-FIX mixed batch: a tool result's after-inject claims its rules `pending`, not `delivered` - hooks/index.ts:claimPending, toolRules - its `context[]` reaches the model only with the next request, so a sibling gated call in the same response now finds the rule pending and is denied with the existing "rule delivered above" line; `turn.step` promotes it exactly like a gate deny. A `prompt.submit` inject stays delivered on the spot (claimDelivered): it rides the user turn, ahead of any tool call of that turn.
- `releaseDelivered` became `releaseClaimed(ledger, loop, paths, state)` - hooks/index.ts - a refused tool carrier releases only the `pending` claims it made, a refused prompt only its `delivered` ones; a pending rule some other deny owns is never released by the wrong carrier.
- Wrappers - rules.ts:normalizeStatement - a loop over leading assignments and the wrappers `env`, `sudo`, `command`, `exec`, each with its own value options (sudo: `-u -g -C -D -h -p -R -r -t -T -U` and long forms; exec: `-a`; env: `-u -C`), short clusters whose last letter takes a value (`sudo -Eu x`), and `--`. Wrappers nest (`sudo env X=1 command git push` reads `git push`). `command -v`/`-V` only looks a name up, so that statement is returned as written and gates nothing.
- Absolute head path - rules.ts:commandName - an unquoted word containing `/` at the head reads as its basename, applied to wrappers too (`/usr/bin/sudo /usr/bin/env ... /usr/bin/git`). Words with quotes are left alone, which keeps the deferred quoted-word case below out of scope.
- `env -S` - rules.ts:pastEnv - `-S <s>`, `-S<s>` and `--split-string=<s>` splice the unquoted, re-split string into the word list in place and keep scanning env's options through it, which is GNU env's own semantics (`env -S "X=1 git -C r push" origin` reads `git push origin`).
- Heredoc - hooks/index.ts:heads, pastBodies - `<<`/`<<-` records the delimiter (quote-stripped via `quotedWord`) and the scan continues on the rest of that line (`cat <<EOF | sh` still sees `sh`); at the next unquoted newline every pending body is skipped in order up to its terminator line (leading tabs stripped for `<<-`), and scanning resumes as a new statement. A body with no terminator runs to the end and the scan stops, the old behaviour. Shared with the gh, rm, pkill and excluded-compound hooks: the full bun suite (their tests included) passes unchanged, plus new gh/rm/pkill cases after a heredoc.
- parseLoad - rules.ts:parse - an inline `load:` value whose next non-blank line is indented throws `load: an inline value cannot be followed by indented lines: <line>`; that rule lands in `buildIndex` as `always` with the error, and the live-dir test fails CI.
- Tests, each failing on HEAD `6052544`'s index.ts/rules.ts (checked on a scratch copy with the new specs: 27 bun fails, the kit's new test fails) and passing now: kit `an after inject and a gated call in one step: the gate still denies; after turn.step it runs` (tests/routing.test.ts); bun `delivery state` (claimPending, releaseClaimed, a tool inject makes a sibling gate wait), `heads: the scan resumes after a heredoc body` (9 cases incl. gh/rm/pkill), `parseLoad` inline-plus-indented, `normalizeStatement: wrappers and path-qualified heads` (7), `matchTool, Bash` (heredoc push gates; sudo/command/exec//usr/bin/git/env -S reach the gate; `sudo -u x echo git push` does not).
### Deviations
- Beyond the five items: a `<<<` here-string no longer stops the scan; its word is skipped as a redirect target. Same bug class as the heredoc (a command after it was invisible), and a here-string has no body to protect.
- `normalizeStatement` returns `command -v ...`/`command -V ...` unstripped; the brief listed `command` with its options, and `-v`/`-V` do not run the command, so stripping them would gate a lookup.
- The unit test `a rule already delivered by context never gates` was renamed `a rule a prompt delivered never gates`: after this fix only a prompt inject is delivered at once, and the old name described the tool-context case it no longer covers.
### Tradeoffs
- `pending` for tool injects vs. a separate "injected" state - the deny's "delivered above" line is already true when inject and deny share the next request, so no new state, ledger type or message.
- Splitting heredoc bodies in `heads` (shared) vs. a router-only pre-pass - one split for every Bash hook, as the doc requires ("after rails' existing statement split"); the gh/rm/pkill hooks gain visibility of commands after a heredoc, which is the correct reading of the shell.
- Option tables per wrapper vs. dropping the first word - dropping misreads `sudo -u x echo git push` as `-u x echo ...`; the synthesis asked for option semantics.
### Open questions
- DEFERRED per synthesis X6CMQgQe item 5: quoted command words (`"git" push`, `git "push"`) still miss the gate (`"git" push` matches nothing, `git "push"` only rides after). The model writes these rarely; unquoting words in `normalizeStatement` would close it, not done here.
- Other wrappers (`nohup`, `time`, `nice`, `timeout`, `xargs`, `bash -c '...'`) are not stripped; out of this round's scope. Say if any should reach the gate.

## Phase 6: Router log
### Design decisions
- The buffer, cap and writer are a `RouterLog` on the `Router` - hooks/index.ts:newRouterLog, appendLine, trimLog, logContent - `say()` appends `<ISO time> <loop> <line>` and pumps; the debug-log line is unchanged (no prefix), so every earlier criterion that quotes the debug log still reads the same.
- Serialized writes - hooks/index.ts:pumpLog - one async loop is the only writer: a flush while it runs sets `queued`, and the loop writes again with whatever the buffer holds then. One in flight, at most one queued, and the last write always carries the whole buffer.
- The writer is bound to the newest `$` a line arrived with - hooks/index.ts:bindLog - a queued write may outlive the hook that queued it (`reference.md:158` allows `$` calls after a hook returns), and the newest `$` is the one most likely still live.
- 1 MiB cap counts UTF-8 bytes of the whole file, marker included - hooks/index.ts:utf8Length, trimLog - the cap is about file size, and `$.fs.write` refuses over 4 MiB in bytes; one line always stays.
- A hot-reloaded module copy reads the session's existing file once and puts it ahead of its own buffer - hooks/index.ts:openLog, seedLog - otherwise the new copy's first whole-file write would erase the earlier copy's lines (the latch reason among them). The dropped-lines marker is parsed back so its count keeps adding up.
- The `session ... start` line is said once per module copy by the first router hook, tagged with that hook's loop - hooks/index.ts:startRouter, routingOff - see Deviations for why not at index build.

### Deviations
- The `rules: session <id> start, routing on|off, CC <version>` line is said at the router's first hook of a module copy, not at index build - same effect, correct seam: the index is only built while routing is on, so a line said there could never read `routing off`. ### Tradeoffs
- Rewrite-the-whole-file per flush vs. a rotating set of chunk files: `$.fs.write` has no append, and coalescing keeps the write count at most one behind the line count; 1 MiB per write is well under the 4 MiB cap.
- `Date` for timestamps and the prune clock vs. `$.clock.now()`: `say()` is synchronous and called from many places; an async clock would make every log line an await. The kit tests use real time with 14-day margins, so nothing is flaky.
- `rm -f` through `$.process.run` vs. leaving old logs: the spec asks for deletion and `$.fs` cannot delete; one argv call per index build, only when something is stale.

## Audit round 2 fixes
Implementation audit round 2 of Phase 6 (synthesis X6CMQgQe, probes P1-P5).
### Design decisions
- One file per module copy, `<sessionId>.<copyTag>.log` - hooks/index.ts:copyTag, logFileName, newRouterLog - `copyTag` is the copy's load time in ms plus six random base-36 characters, so two loads in one millisecond still differ and `ls` sorts a session's copies by load. Two copies never share a file, so neither can overwrite the other (P4). `seedLog`, `DROPPED_MARKER` and the `$.fs.read` in `openLog` are gone; the Phase 6 decision "a hot-reloaded module copy reads the session's existing file once" is superseded.
- P3 (a rejected read erasing an existing log) has no path left: `openLog` reads nothing, and no other `$.fs.read` touches the log directory. Pinned by the kit test `the log never reads a file back`.
- `routerFailed` opens the log itself before latching - hooks/index.ts:routerFailed - so a failure before `startRouter` ran (P1: `$.state.get` rejects inside `loadRouter`) still lands its `failed` and `routing off` lines in the file, and `failedStatus` gets the real path. It awaits `openLog` only, which is `$.env.get('HOME')` and `$.session.id()`, never the file system; the start line is fired beside it.
- `routingOff` fires `startRouter` and awaits only `loadRouter` (P2) - hooks/index.ts:routingOff - so a log that never opens cannot hold the `rule_routing:false` latch or its `invalidate`. Lines said before the log opens stay in the buffer and go out with the first write.
- The start line is put first in the buffer whenever it is ready - hooks/index.ts:prependLine, say(first) - because it is no longer awaited before routing, the index and drop lines can be said before it; prepending keeps it the file's first line deterministically. Its timestamp is when it was said, so it can read a few ms later than the line after it.
- The start line reports the state the session started in, `r.routing` and the latch `loadRouter` read back from `$.state` (new `Router.held`), not `r.off` at the moment it is said: with the start line off the decision path, `r.off` may already hold a latch set after start, which has its own `routing off` line.
- `session.end` with reason `clear` or `resume` closes the current file with `rules: session <id> end (<reason>), the next session logs to its own file` and replaces `r.log` and `r.started` - hooks/index.ts:endSession, the `session.end` hook - so the next hook opens a file under the new `$.session.id()` and says a new start line (P5). The old `RouterLog` finishes its in-flight write on its own.
- Pruning goes through `rkvr rmrf --` - hooks/index.ts:findRkvr, pruneLogs - per rules/safety.md (router logs are not regenerable, no exceptions). `findRkvr` walks the engine's `PATH` (absolute entries only), then `~/.cargo/bin/rkvr`, each checked with `$.fs.exists` at run time; with none found nothing is deleted and the log says `rules: prune skipped, no rkvr on PATH or at <home>/.cargo/bin/rkvr: <n> router logs older than 14 days kept`. `rkvr rmrf -- <files>` was checked by hand to accept `--` (archive under `/var/tmp/rmrf`, exit 0).
- `pruneLogs` is fired beside the index build, not awaited by it - hooks/index.ts:buildRules - an `rkvr` archive (tar + gzip, 30 s run timeout) has no business in the first attachment's path. The kit test waits for the writes to settle before asserting.
- Tests added, each failing on af3a76a (run by copying `git archive af3a76a` rails to scratch with the new spec files): bun `prependLine puts the start line first`, `every module copy gets its own tag` (old: `tag` undefined), `neither copy loses a line of the other` (two `register()` copies, one engine with 5 ms delayed writes; old: `rules: keep a1.md`, `a2.md`, `a3.md` lost from the shared file); kit `a latch before the log opened still reaches the file` (old: no file, status `log unavailable`), `the log never reads a file back` (old: read the log path), `a log that never opens does not hold up the rule_routing false latch` (old: timed out at 5 s), `after /clear the new session id gets its own file` (old: no `sess-2` file under any name), `without rkvr nothing is deleted and the log says so`. ### Deviations
- P5 resets only the router log on `/clear`/resume, not the ledger or the latch: whether those should also reset across `/clear` predates Phase 6 and was flagged out of scope by the synthesis.
- `routerFailed` still awaits `openLog` (HOME and session id), so a hang in those two engine getters would hold the failure path's latch; the brief's P2 bound is the routing decision path, which no longer awaits the log at all. Same effect, correct seam: the status line cannot name a real path without them.
### Tradeoffs
- One file per copy vs. re-reading the file before each write: re-read-before-write still races between copies (synthesis item 1); separate files cannot. Cost: a hot-reloaded session's log is several files, read with `ls <id>.*.log` in name order.
- `PATH` walk then `~/.cargo/bin` vs. a hard-wired `~/.cargo/bin/rkvr`: the walk finds whichever `rkvr` the engine would run; the fallback covers an engine launched with a short `PATH`. Up to one `$.fs.exists` per `PATH` entry, only when something is stale.
